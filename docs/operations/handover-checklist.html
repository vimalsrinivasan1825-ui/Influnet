▶

A placeholder secret means forgeable signatures — anyone could mark a payment captured. Decide the paid-plan switch before launch

▶

SUBSCRIPTIONS_ENABLED=false means the paid tier is absent, not merely unpurchased: no pricing, no upgrade prompt, and /api/billing/checkout returns 404. Flipping it later, on a live user base, retroactively puts existing users over limits they never agreed to.

Part 2 — Running it yourself for the first month or two

The goal of this phase isn't features. It's to learn what actually breaks, so the next owner inherits knowledge instead of guesses.

Set up the weekly 30-minute review
recurring
▶
  1. /dashboard/admin/health — every required integration configured, 0 migrations pending.
  2. Sentry — triage new issue groups. An issue seen 200 times by 1 user is a loop; once by 200 users is a release regression. Different urgency, different fix.
  3. Resend — bounce and complaint rate. Above ~2% complaints, stop sending and find out why before the domain is burned.
  4. Supabase → Reports — watch egress and realtime connections, not database size. Size is the least binding limit on this product; egress and connection count bind first.
  5. Razorpay — every capture has a matching opened gate. A mismatch is a webhook problem, not an accounting one.
  6. Azure — replica count over the week. If you're regularly at max, the ceiling is now a availability limit rather than a cost guard.
  7. Dependabot — merge patch-level PRs weekly. A quarterly batch is a scary batch.
Start an incident log on day one
recurringhighest handover value
▶

One file. One line per incident: what the user saw · what it actually was · what fixed it.

This repo's most valuable documents are exactly that shape — .agents/lessons_learned.md and the audit reports. A month of real-user incidents is the single most useful thing you can hand a new developer, and it's the one thing that cannot be reconstructed afterwards. Write the line the day it happens; you will not remember it in March.

Two things that will generate most of your support load
reference
▶

"My project is stuck." The stage machine has three exits, not one — mutual sign-off (8 of 12 stages), advance (only sent_for_review and revisions), and confirm_completion (final_payment only). ALLOWED_TRANSITIONS in packages/core is the only truth, and it is not the array order. Never unstick a project by editing stage_progress by hand — use record_stage_signoff() / revoke_stage_signoff().

"X/Twitter won't verify." Apify's free plan returns {demo:true} stubs for the third-party X actor. That's the cause, not a bug — it needs a plan upgrade or a different actor. Instagram and Facebook are unaffected.

Part 3 — Handing it to another developer

"Handover complete" means a competent stranger ships a fix on day two without calling you.

Write the access inventory — the part that only exists in your head
you only~2 hours
▶

In a password manager — not this repo, not a doc. For each of: Supabase (×3, two accounts) · GitHub · Azure (×2 accounts) · Railway · Cloudflare/DNS · Razorpay · Resend · Stream Chat · Apify · Sentry · Upstash · Expo/EAS · Apple Developer · Google Play · 2Factor · Cloudinary —

  • who owns it, and whose personal email it's tied to;
  • what it costs and when it renews;
  • whether the new developer gets their own login or inherits yours.
Two traps already paid for once. A Resend key from a different account silently broke staging email — keys must belong to the account that owns the verified domain. And the active gh CLI account lacks repo admin, so admin API calls 404 and read as "this doesn't exist" — don't let a new developer conclude branch protection is missing because of it.
Rotate credentials at handover
you only
▶

Anything the outgoing party has seen gets rotated when they leave; anything the incoming party will see is now shared. At minimum: service-role keys, RAZORPAY_KEY_SECRET, RAZORPAY_WEBHOOK_SECRET, STREAM_API_SECRET, RESEND_API_KEY, SUPABASE_ACCESS_TOKEN.

EMAIL_UNSUBSCRIBE_SECRET is the exception — rotating it invalidates every unsubscribe link already sitting in someone's inbox. Rotate that one only if it actually leaked.

Housekeeping first. ADMIN_CREDENTIALS.local.txt sits in the repo root, alongside several *-backup-*.json data dumps. Confirm they're gitignored and delete the stale ones before granting anyone repo access.
