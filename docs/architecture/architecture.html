Module map — engineering handbook

The section above is a status board. This one is the wiring diagram a developer opens before touching code. Every feature is written as a self-contained module with a clear boundary, so you can work inside one without breaking another. Each entry answers five questions: what files it owns, what it depends on, what data it touches, how a request flows through it, and where you start debugging when it breaks.

Read a module as a contract, not a folder. A module exposes one inbound surface (an API route, an edge function, or a React view) and reaches other modules only through named, stable seams — never by importing another feature's internals. Those seams are:

UI · React page/view API · /api route (server) RPC · Postgres function RLS · row-level security EDGE · Supabase edge function EXT · third-party service STORE · Zustand client state
The one rule that keeps modules independent: a feature never imports another feature's files. Everything shared lives in the Shared kernel (lib/, types/, store/). Cross-feature effects happen in the database (an RPC or a trigger), not in application code. That is why accepting a collab request can create a project, a conversation, and a notification without the requests module ever importing the projects, messaging, or notifications modules.

Shared kernel — the spine every module depends on

Shared kernelAuth guard · fetch client · types · validators · stores

The only code every feature is allowed to import. Change it deliberately — a breaking edit here ripples everywhere. It has no feature logic of its own; it only provides the seams.

Ownslib/api.ts (server auth: withAuth / withAdmin / jsonError), lib/api-client.ts (apiFetch + bearer token), lib/supabase/* (browser / server / RSC / proxy clients), lib/validators.ts (Zod, snake_case), types/index.ts (Database + domain models), lib/constants.ts, store/auth-store.ts, store/notification-store.ts
Inbound seamServer: every /api/* route calls withAuth(req) → verifies the JWT, loads the profile role, returns a Supabase client scoped to the caller. Client: every UI calls apiFetch(path) → injects Authorization: Bearer <session token>.
Depends onSupabase Auth (JWT verification) only. Depends on no feature module — features depend on it.
Auth flow
  1. UI reads live session token via getAuthToken() (never localStorage).
  2. apiFetch attaches it as a bearer header.
  3. withAuth re-derives the user from the token + reads profiles.role.
  4. Route runs queries with the caller's JWT, so Postgres RLS is the real gate.
Debug fromlib/api.ts:41 (withAuth) logs 401/403 with reasons; lib/api-client.ts never throws on empty bodies. A "works in UI, 401 in API" bug is almost always a stale/absent bearer token.
Boundary: features may import from lib/, types/, store/ — never from each other. Adding a table? Update types/index.ts Database type so withAuth's client stays typed.
Session & edge middlewareUI · proxy · runs before every page

Refreshes the Supabase session cookie on every navigation and enforces logged-in / logged-out routing. In Next.js 16 the old middleware.ts convention is renamed proxy.ts and must sit beside app/ in src/.

Ownssrc/proxy.ts, lib/supabase/middleware.ts
Depends onShared kernel (Supabase SSR client). No feature module.
Flow
  1. Request hits proxy before the page renders.
  2. Supabase SSR client reads/rewrites the auth cookie, refreshing the token if near expiry.
  3. Logged-out users hitting a private route → redirect to /login; logged-in users hitting /login → bounced to /dashboard.
Debug fromsrc/proxy.ts. Symptoms: infinite redirect loops, or being logged out on refresh → check cookie set/get and the public-route allowlist.
Boundary: public routes (/c/*, /b/*, /influnet/*, /login, /signup) must be whitelisted here or SSR profiles 404 for logged-out visitors.

The golden rule for scaling this codebase

  • Features never import features. If module A needs something from module B, it goes through an API route, an RPC, or a shared-kernel helper — never a direct file import. If you find yourself importing across features, that logic belongs in the Shared kernel or the database.
  • Cross-module effects live in Postgres. One action touching many modules (accept → project + conversation + notifications) is an atomic RPC + triggers, so each feature stays small and testable in isolation.
  • The database is the real API. RLS is authorization; API routes are thin. To reason about "can this user do X", read the policy, not the route.
  • Schema is append-only. Never edit a shipped migration — add the next numbered file. The migration list is the system's real change log.
  • Swap an external, not the app. Stream, 2Factor, and the email provider each sit behind one seam (lib/stream.ts, the OTP edge fn, Supabase Auth). Replacing any of them touches exactly one module.
